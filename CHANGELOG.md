# Changelog

## 0.2.0

Minor release: the public types of the `migratr` and `migratr-format` libraries change in ways that break code built against 0.1. `Op` is now `#[non_exhaustive]` and has four new variants; `Op::CreateTable` gains `checks` and `unique`, and `Op::CreateIndex` gains `where_clause`; `IndexDef.columns` and `Op::CreateIndex.columns` change from `Vec<String>` to `Vec<IndexColumn>`; and `MigrateError`, which is not non-exhaustive, gains `NoSuchForeignKey` and `TriggerMismatch`. A 0.1.5 would be picked up by every `^0.1` dependent and fail its build, as smugglr's did. The migration file format only gains fields and operations, every existing file keeps its checksum, and the ledger's schema is unchanged, with no schema migration.

The relationships release. A migration can now add a foreign key to a table that already exists, drop one, give a table CHECK and composite UNIQUE constraints, and create or drop a trigger, all as typed operations rather than `raw_sql`. Indexes can be partial, built on an expression, descending, or collated. The table rebuild these operations depend on no longer turns foreign keys off or creates TEMP objects, which D1 refuses, so the same rebuild now runs on a local file and on a D1 database. A table that other tables reference is rebuilt together with them.

### New
- **`add_foreign_key`, `drop_foreign_key`, and partial, expression and descending indexes** (PR #69, #66): `{"op": "add_foreign_key", "table", "columns", "references": {"table", "columns"}, "on_delete", "on_update"}` rebuilds its table with a table-level `FOREIGN KEY` item added and keeps every row and index; a key that references its own table works the same way. The rows already in the table are the check: before any change, `up` counts the rows whose key columns are all non-NULL and name no parent row, and refuses with `ForeignKeyViolation` naming the table and that count. `plan` now makes the same count, so it refuses with the same error as `up` would. `drop_foreign_key` carries the key's definition and removes either a table-level `FOREIGN KEY` item or the one column's inline `REFERENCES` clause. When the table has neither, it refuses with the new `MigrateError::NoSuchForeignKey` (`--json` code `no_such_foreign_key`). Each of the two is the other's inverse, so `down` reverses both. `create_index` takes a `where` clause for a partial index, and each entry in `columns` is either a bare column name or an object with exactly one of `name` or `expr`, plus optional `desc` and `collate`, written as `<key> COLLATE <name> DESC`. A key that is only a name parses as `IndexColumn::Name` whether it is written as `"a"`, `{"name": "a"}` or `{"name": "a", "desc": false}`, so all three spellings give the same checksum (PR #72, #71). Reversing a `create_index`, or a `drop_index` of a partial index, keeps its `WHERE` clause. The new `Executor::missing_parents` and `Executor::foreign_key_violations` are default methods that return `None`, so an existing `Executor` still compiles. `RusqliteExecutor` overrides both, and any other executor can do the same through the exported `migratr::missing_parents_through` and `migratr::foreign_key_violations_through` over a `SqlReader`.
- **Table CHECK and UNIQUE constraints, and `create_trigger` and `drop_trigger`** (PR #70, #59; PR #72, #71): `create_table` takes `checks` and `unique` and writes them after the `PRIMARY KEY` item as `CHECK (...)` and then `UNIQUE (...)`, in the order given. Each check is an expression kept verbatim, or `{"name", "expr"}`, which is written as `CONSTRAINT "name" CHECK (expr)`; each unique entry is a list of columns. Both fields are omitted from the canonical JSON when empty, so files written before this release keep their checksums. The order of checks, of unique lists, and of the columns in each is part of the checksum, and the rustdoc says so. `create_trigger` holds a `TriggerDef` (`name`, `table`, `sql`) and runs `sql` verbatim, hashed exactly as written, whitespace included. `drop_trigger` carries the same definition, and each operation is the other's inverse. A `create_trigger` whose `name` or `table` differs from what its statement names is refused before anything runs, with the new `MigrateError::TriggerMismatch` (`--json` code `trigger_mismatch`) naming both. Before this check, such a trigger applied and its `down` then failed with "no such trigger". `drop_trigger` counts as destructive, as `drop_index` does, so it takes a snapshot first. `migratr new drop_<name>` now looks for a trigger in `schema.json` after tables and indexes, and copies the trigger's definition into the new file.

### Changed
- **A rebuild uses no TEMP objects, leaves foreign keys on, and rebuilds a referenced table with the tables that reference it** (PR #68, #67): `up` now always calls `run_atomic` with `suspend_foreign_keys` false, and no rebuild statement creates a TEMP table or trigger or sets `foreign_keys`. The family is the rebuilt table plus every table with a foreign key that references it. Each table in the family gets a new table whose references name the new parent (for a self-reference, its own new table). The rows are copied parents first, the old child tables are dropped before the old parent, and the new tables are renamed with the parent first, so SQLite rewrites the references to the final names and nothing is left under a temporary name. The foreign-key check used to run inside the transaction after the copy, over the whole database, through a TEMP table whose trigger raised an error. Now the rows a foreign key would refuse are counted before any change, only over the family's tables, through `Executor::foreign_key_violations`, and a non-zero count refuses with `ForeignKeyViolation` naming the table and the count. An executor that keeps the default `None` gets no count. Its copy then fails on such a row inside the atomic run, which returns `MigrateError::Apply` rather than `ForeignKeyViolation`, and nothing changes. A database whose foreign-key violations are only in tables the rebuild does not touch is no longer refused.

## 0.1.4

Patch release: one trait and two functions added to the existing `migratr` library API, with no change to the CLI, the migration file format, or the ledger's schema, and no schema migration.

The shared-reader release. A program that drives migrations over something other than a rusqlite connection can now read a database's schema and ledger through migratr itself, by supplying only a way to run a SQL statement and return its rows as JSON. Until now such a caller had to copy those reads, as smugglr's `--migratr` does for its `Executor` over HTTP-SQL. `RusqliteExecutor` now reads through the same code, so the queries and decoding exist once. It returns the same schema and ledger as before, though some of the errors it returns for a malformed row are different variants of `rusqlite::Error`.

### New
- **One reader of the schema and ledger, for any way of running SQL** (PR #56, #55): the new `migratr::SqlReader` trait has two methods: `rows(sql)` runs a statement and returns its rows as `Vec<Vec<serde_json::Value>>`, and `malformed(what)` builds the caller's error for a row that is not what its statement promises. `migratr::read_schema_through(&mut reader, skip)` returns the same `SchemaSnapshot` that `Executor::read_schema` returns, and `migratr::read_ledger_through(&mut reader)` returns the ledger rows ordered by version, or an empty list when `_migratr_migrations` does not exist. The `skip` predicate names tables the reader must not touch, such as a host's own: a skipped table is not queried, and every `sqlite_master` object on it, such as an index, is left out of the snapshot. A value of the wrong type, a row with too few columns, and a negative ledger version are all errors. A test in `crates/migratr/tests/reader.rs` reads one database through a JSON-row reader and through `RusqliteExecutor` and asserts that the schema and the ledger match. All three items build with default features off.

### Changed
- **`RusqliteExecutor` reads through the shared reader, which changes some error variants** (PR #56, #55): `read_schema` and `read_ledger` are now thin calls into `read_schema_through` and `read_ledger_through`, and return what they returned before for a well-formed database. A negative ledger version used to return `rusqlite::Error::IntegralValueOutOfRange` and now returns `rusqlite::Error::InvalidColumnName` carrying the text "a negative ledger version". A row of the wrong shape now returns that same variant with a description in place of rusqlite's own conversion error, and a blob where text is expected fails as "a value that is not text", because the reader sees a blob as null. Code that matches on those specific variants needs updating; the refusal itself is unchanged.

## 0.1.3

Patch release: two additive functions in the existing `migratr` library API, with no change to the behavior of `up` or `down`, the CLI, the migration file format, or the ledger's schema, and no schema migration.

The rebuild-and-record release. A program holding an `Executor` can now ask whether a migration would rebuild tables on a given database before running anything, and can mark a migration as applied on a database that already has its shape, without running it. Both exist for callers that drive migrations themselves, the first being smugglr's `--migratr`. Alongside them, the release procedure picks up two corrections from its first end-to-end run, and the workspace gains a runner for acceptance scenarios.

### New
- **The library says which tables a migration rebuilds, and records a migration without running it** (PR #52, #51): `migratr::rebuild_tables(&schema, &migration)` takes a schema read through `Executor::read_schema` and returns the tables `up` would rebuild, each named once in operation order, or an empty list when the migration needs no rebuild. It counts a dropped column only when the column needs the rebuild, discounts an index the migration dropped first, and refuses with `UnparseableTable` when a dropped column's table has a `CREATE` statement that does not split. The decision moved into one function that `up` now calls too, so the report cannot drift from what `up` does, and `up`'s tests are unchanged. The report covers tables only: `up` still refuses a migration whose rebuild is not its first operation, even though `rebuild_tables` names that table. `migratr::record_applied(&mut exec, &migration)` writes the migration's ledger row, with the migration's checksum, through any `Executor`, creating `_migratr_migrations` when it is absent and running none of the migration's operations. The ledger and the row land in one atomic run, so a failure returns `MigrateError::Apply` and leaves no ledger, and a version the ledger already holds is refused the same way. A later `up` treats the recorded migration as applied and does not run it. Both functions build with default features off.
- **Acceptance scenarios run under `cargo test`** (PR #43, #35): `rstest`, `rstest-bdd`, and `rstest-bdd-macros` are now workspace dev-dependencies, and `crates/migratr-cli/tests/bdd.rs` runs every `.feature` file under that crate's `tests/`, so scenarios run in the existing CI workflow with no new one. A scenario with no matching step code fails the test, and the failure names the scenario. One `@smoke` scenario proves the wiring against behavior migratr already documents: `restore` without `--yes` exits 1 with the error code `restore_not_confirmed`. `CLAUDE.md` says where scenarios live and that they are generated from the legion requirement, never hand-edited. Nothing published changes, since these are test-only dependencies.

### Fixed
- **The release procedure's issues carry criteria, and its live-site wait follows the deploy** (PR #42, #33): both faults were found by the 0.1.2 release, the first run of `RELEASING.md` end to end. Steps 3 and 9 created issues whose body was a bare sentence, and the pr-write gate needs an issue to map, so those bodies now put the criterion under an `## Acceptance criteria` heading. Step 11 used to fetch the smugglr.dev pages up to 30 times, 60 seconds apart, until they showed the new version, but WebFetch caches a URL for 15 minutes. It now polls the `Workers Builds: smugglr-shingle` check on shingle's merged commit every 20 seconds for up to 30 minutes, and once that check reports `success` it fetches each page with `?r=X.Y.Z` on the URL, which gets past the cache, and confirms the version.

## 0.1.2

Patch release: new installer and release tooling around the existing binary, with no change to any crate's code, the library API, the CLI, the migration file format, or the ledger.

The installer release. migratr now has a one-line install: `curl -fsSL https://raw.githubusercontent.com/rafters-studio/migratr/main/install.sh | bash` downloads the newest published binary for the machine, verifies it against the release's checksums, and puts it on the PATH, with no version written into the script, so each release updates the installer without anyone editing it. Alongside it, migratr is now released by one agent run with no operator step, following a written procedure that bumps the version, writes this changelog, merges the release PR, tags it, and publishes the changelog to smugglr.dev.

### New
- **`install.sh` installs the latest migratr release** (PR #34, #32): run as `curl -fsSL <url> | bash`, the installer at the repo root detects the platform (`linux` or `macos`) and architecture (`x64` or `arm64`, preferring the native arm64 build when a macOS shell runs under Rosetta 2), resolves the version, downloads `migratr-<os>-<arch>.tar.gz` and `checksums.txt` from that GitHub release, and refuses to install unless the archive's SHA-256 matches its line in `checksums.txt`. The version comes from the first argument (`bash -s v0.1.1`), then `MIGRATR_VERSION`, then the tag the `releases/latest` redirect points at. It installs to `MIGRATR_INSTALL_DIR` (default `~/.local/bin`) and, when that directory is not on the PATH, appends a PATH line to `.bashrc`, `.zshrc`, or fish's `config.fish`, only if it is not already there. It uses `curl` or falls back to `wget`. Platforms with no published build (Windows, linux-arm64) are refused before any download with a pointer to `cargo install migratr-cli`. The install ends by running `migratr --version`; a binary that fails to run is reported as an install error, not a success. `scripts/test-install.sh` runs the installer against real published releases, and CI runs it on Linux and macOS.
- **Releases run with no operator step** (PR #36, PR #37, PR #38, #33): `RELEASING.md` is the procedure an agent follows to release migratr from a clean `main` to a live smugglr.dev page, stopping and reporting on the first failure. `release.toml` declares the version file (`workspace.package.version` in `Cargo.toml`), this changelog, the tag format `v{version}`, the preflight commands (fmt, clippy, tests, and the release-script tests), and the shingle docs branch. `scripts/release.sh` and `scripts/sync-version.sh` are copied from legion with two patches: the version bump also moves the `version` pin on every `path = "..."` dependency between the workspace crates, and `--activate` is refused. The bump level is read from the first line of the new changelog entry (for this entry, `Patch release:`). After `release.yml` publishes the GitHub release, polled with `gh` rather than `curl` so legion's network hook cannot stall the run, the procedure copies `CHANGELOG.md` into shingle and merges a docs PR so https://smugglr.dev/migratr/changelog/ shows the new entry. `scripts/test-release.sh` covers the scripts, skips its legion-backed cases when legion is not installed, and runs in CI.

## 0.1.1

The release-pipeline release. Pushing a `v*` tag now builds the `migratr` binary for four platforms, attaches them to a GitHub release with checksums, and publishes the four workspace crates to crates.io, so a release needs no manual step. Alongside it, the refusal for an edited applied migration now tells the user what to do instead of only what went wrong. Patch release: a message rewording within an existing error (the `checksum_mismatch` code is unchanged) and new release automation, no API change, no change to the migration file format or the ledger.

### New
- **A pushed tag releases migratr** (PR #29, #28): `.github/workflows/release.yml` runs on any `v*` tag. It builds `migratr-cli` in release mode for `x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, and `x86_64-pc-windows-msvc`, packages each as `migratr-<os>-<arch>.tar.gz` (or `.zip` on Windows), and creates a GitHub release carrying the archives, a `checksums.txt` of their SHA-256 sums, and generated release notes. A parallel job publishes to crates.io through trusted publishing (`rust-lang/crates-io-auth-action`, no stored token). Before publishing anything it refuses unless the tag equals `v` plus the `version` in `[workspace.package]` of `Cargo.toml`. It then publishes in dependency order (`migratr-format`, `migratr-macros`, `migratr`, `migratr-cli`), skipping any crate whose version is already in the crates.io index and treating cargo's "already exists" as success, so a run that failed partway can be re-run and publishes only what is missing.

### Fixed
- **The checksum-mismatch refusal says how to recover** (PR #27, #24): when an applied migration's file has been edited, `up` and `down` (and `Migrator::status`) refuse with `MigrateError::ChecksumMismatch`. The message used to say only that the checksum no longer matched the ledger. It now reads "migration `<version>_<name>` was edited after it was applied. Applied migrations are not edited: restore the file to what was applied, then write a new migration for the change". The same text reaches the CLI's `--json` error document under the unchanged `checksum_mismatch` code, and tests in both the library and the CLI pin it.

## 0.1.0

The first release. migratr manages SQLite schema migrations written as JSON files, applies them atomically against a ledger, rebuilds tables safely where SQLite cannot alter in place, reverses only what has an exact inverse, and snapshots the database before any destructive step. It ships as a library (`migratr`, with an `embed!` macro and `Migrator` for migrations compiled into a program) and as a CLI (`migratr`) with machine-readable `--json` output.

### New
- **Migrations as JSON files** (PR #12, #2): each migration is a JSON file of typed operations named by version and name. The parser reports the exact JSON path of a bad field, lists every file that shares a version, and computes a checksum per file so an edit after apply is detected.
- **Ledger and `up`** (PR #13, #3): applied migrations are recorded in a ledger table. `up` applies each pending migration and its ledger row in one atomic run; a failure rolls it back and names the failing statement and operation. `up` refuses to run when an applied file was edited or a ledger row has no file.
- **Safe table rebuilds** (PR #14, #4): an operation SQLite cannot do in place, such as dropping a column it refuses to drop, rebuilds the table by SQLite's 12-step procedure, editing the stored `CREATE TABLE` text with a comment- and quote-aware scanner. Indexes, triggers, and dependent views are recreated after the row copy, rowids and `sqlite_sequence` carry over, and `foreign_key_check` runs before commit. A rebuild is refused before anything runs when the table's `CREATE TABLE` does not parse, when another object uses the dropped column or the table's columns by position, or when the rebuild is not the first operation in its migration. The rebuild is checked against a hazard oracle covering nine SQLite rebuild hazards (PR #16, #5).
- **`down` reverses only exact inverses** (PR #15, #6): `down` reverses the newest N applied migrations, newest first, each with its ledger delete in one atomic run. Following the Rails rule, an operation with no exact inverse makes the whole range refuse with `irreversible` before anything runs. `down` reverses structure only, and says that data in dropped objects is not restored.
- **Snapshots and restore** (PR #17, #7): before a destructive step in `up` or `down`, migratr copies the database into `.migratr/snapshots/` next to it and keeps the newest snapshot; a snapshot that cannot be written stops the step. `restore` replaces the database with the latest snapshot, or a named one, and changes nothing without `--yes`.
- **`schema.json` and `new`** (PR #18, #8): after every successful `up` and `down`, migratr writes `schema.json` in the migrations directory describing the resulting schema. `new` scaffolds a migration file from a Rails-style name and column specs (such as `create_users id:integer:pk`), checked against `schema.json`.
- **`embed!` and `Migrator`** (PR #21, #10): `migratr::embed!("migrations")` embeds a migrations directory in the program and parses it at compile time with the library's own parser, so a malformed file stops the build. `Migrator` offers `up`, `down`, `status`, and `plan` over the embedded set.
- **The CLI, with `--json`** (PR #20, #9): `migratr [--db PATH] [--dir PATH] [--json] <new|up|down|status|plan|restore>`. `plan` prints the statements a run would execute, which steps are destructive, and the snapshot each would take, changing nothing. With `--json`, each command writes one JSON document to stdout carrying `command` and `status`; a failure adds a stable error `code` and `message` and exits non-zero (2 for usage errors, 1 otherwise).
- **Published to crates.io** (PR #26, #25): the workspace publishes as `migratr-format`, `migratr-macros`, `migratr`, and `migratr-cli` under the MIT license, with CI verifying each crate builds from its own package.
